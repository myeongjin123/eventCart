# 부하 테스트 결과

- 3단계: 비관적 락만 쓴 기준치
- 4단계: Redis 재고 게이트 추가 후 같은 조건으로 재측정 → [비교](#4단계-redis-재고-게이트-적용-후)

## 조건

| 항목 | 값 |
|---|---|
| 도구 | k6 0.54 (`load-test/order-rush.js`) |
| 환경 | GitHub Actions `ubuntu-latest` (2코어), 앱·MySQL 8·k6가 **한 대**에서 실행 |
| 앱 | Spring Boot 3.5, HikariCP 기본 10개, JVM 워밍업 없음 |
| 부하 | 회원 500명이 1번씩 바로 구매, 동시 사용자(VU) 100 |
| 재고 | 합계 100개, 1인 1개 |
| 시나리오 | **hot**: 상품 1개에 재고 100 / **spread**: 상품 10개에 재고 10씩 |
| 처리량 계산 | 회원가입·로그인(setup)을 뺀 주문 구간만: 주문 수 ÷ (마지막 응답 − 첫 요청) |

## 3단계 결과: 비관적 락만 (2회 실행, 2026-11-25)

| 시나리오 | 회차 | 성공 / 품절 / 오류 | 처리량 | 평균 | p50 | p95 | p99 |
|---|---|---|---|---|---|---|---|
| hot | 1 | 100 / 400 / 0 | 125.9 건/초 | 744 ms | 617 ms | 1,467 ms | 1,672 ms |
| hot | 2 | 100 / 400 / 0 | 110.5 건/초 | 836 ms | 713 ms | 1,497 ms | 1,679 ms |
| spread | 1 | 100 / 400 / 0 | 309.8 건/초 | 290 ms | 276 ms | 659 ms | 835 ms |
| spread | 2 | 100 / 400 / 0 | 234.7 건/초 | 380 ms | 334 ms | 953 ms | 1,284 ms |

- 실행 기록: [1회차](https://github.com/myeongjin123/eventCart/actions/runs/45592729201), [2회차](https://github.com/myeongjin123/eventCart/actions/runs/45593275265)

## 해석

1. **정합성은 부하에서도 지켜진다.** 네 번 모두 정확히 100건만 성공했고 남은 재고 0, 오류 0.
2. **같은 행에 몰리면 느려진다.** 상품 1개에 몰린 hot은 spread보다 처리량이 약 2.1~2.5배 낮고 p95는 약 1.5~2.2배 길다. 모든 주문이 한 행의 락 앞에 한 줄로 서기 때문이다.
3. **품절 요청도 줄을 선다.** 500건 중 400건은 결국 품절인데, 재고가 0인지 확인하려고 똑같이 락을 기다린다. 끝까지 기다린 사용자가 "품절"을 받는 데 1초 넘게 걸린다.
4. **DB 커넥션도 같이 묶인다.** 락을 기다리는 동안 커넥션(기본 10개)을 쥐고 있어서, 같은 시간에 들어온 다른 API(조회 등)도 커넥션을 기다릴 수 있다.

→ 4단계 목표: **재고 확인을 DB 앞(Redis)으로 옮겨**, 품절 요청은 락 없이 바로 돌려보내고 DB 락 경합을 줄인다.

## 4단계: Redis 재고 게이트 적용 후

같은 조건(회원 500, VU 100, 재고 100, 2코어 러너). 성공·품절 응답 시간을 따로 잰다.

| 시나리오 | 회차 | 성공 / 품절 / 오류 | 처리량 | p50 | p95 | 성공 p50 / p95 | 품절 p50 / p95 |
|---|---|---|---|---|---|---|---|
| hot | 1 | 100 / 400 / 0 | 303.0 건/초 | 36 ms | 1,398 ms | 1,152 / 1,567 ms | 31 / 51 ms |
| hot | 2 | 100 / 400 / 0 | 191.1 건/초 | 66 ms | 2,224 ms | 1,915 / 2,469 ms | 55 / 113 ms |
| spread | 1 | 100 / 400 / 0 | 511.8 건/초 | 139 ms | 537 ms | 382 / 701 ms | 122 / 235 ms |
| spread | 2 | 100 / 400 / 0 | 360.0 건/초 | 220 ms | 549 ms | 379 / 690 ms | 200 / 409 ms |

- 실행 기록: [1회차](https://github.com/myeongjin123/eventCart/actions/runs/45598618093), [2회차](https://github.com/myeongjin123/eventCart/actions/runs/45599072188)
- 사전 초기화 전 첫 측정([기록](https://github.com/myeongjin123/eventCart/actions/runs/45597920317))에서는 hot p95가 3.0초로 오히려 늘었다. 첫 주문 100건이 동시에 Redis 키 초기화(DB 조회)를 하느라 커넥션 풀에 몰렸기 때문이다. 이벤트 상품 등록 직후 미리 채우도록 바꾼 뒤 위 결과가 나왔다.

### 3단계 대비 (hot, 2회 범위)

| 지표 | 3단계 | 4단계 | 변화 |
|---|---|---|---|
| 처리량 | 110~126 건/초 | 191~303 건/초 | 약 1.5~2.7배 |
| 전체 p50 | 617~713 ms | 36~66 ms | 약 10배 빠름 |
| 품절 안내 p50 | (전체와 비슷, 락 대기) | 31~55 ms | 락을 안 기다림 |
| 성공 주문 p95 | (분리 측정 안 함) | 1.6~2.5 초 | 아래 참고 |
| 초과 판매 | 0 | 0 | 정합성 유지 |

### 해석

1. **품절 요청이 줄을 서지 않는다.** 400건의 품절 요청이 DB 락을 기다리지 않고 Redis에서 바로 409를 받는다(p50 30~55ms). 전체 중앙값이 약 10배 빨라진 이유다.
2. **DB에 가는 요청이 재고 수(100건)로 줄었다.** 그만큼 커넥션과 락을 덜 쓴다.
3. **성공 주문은 여전히 한 줄로 선다.** DB가 최종 기준이라 성공 100건은 여전히 한 행의 락을 차례로 지나간다. 1건당 수십 ms × 100건이라 마지막 성공자는 1.5~2.5초 기다린다.
4. **다음 개선 후보**
   - 락을 쥐는 시간 줄이기: 락 안의 조회(누적 구매 수량) 줄이기, 원자적 `UPDATE ... WHERE remaining >= ?`로 차감
   - 주문 접수와 처리를 분리: Redis 예약 성공 시 "접수됨"으로 바로 응답하고 DB 저장은 큐(대기열)로 비동기 처리



- 2코어 러너 한 대에서 앱·DB·부하기를 같이 돌려 절대 수치는 운영 환경과 다르다. **같은 조건의 전후 비교용**으로 쓴다.
- 회차별 편차(약 10~25%)가 있다. 러너 CPU 모델이 회차마다 달랐다.
- JVM 워밍업 없이 측정했다. 첫 요청 일부가 JIT 컴파일 전이라 느릴 수 있다.

## 다시 실행하기

- GitHub: Actions → **Load test** → Run workflow (회원 수·VU 변경 가능), 결과는 실행 페이지 Summary에 표로 표시
- 로컬: 앱 실행 후 `k6 run -e MODE=hot load-test/order-rush.js`
